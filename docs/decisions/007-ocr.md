# 007. OCR engine: Tesseract (local, offline), behind a replaceable `OCREngine` interface

## Problem

`ImageProcessor` and `PDFProcessor` (for pages with no native text layer) need to turn a raster image into text. The assignment requires this to work for printed and (as best-effort) handwritten scans, must not depend on an external/cloud service, must work in local Windows development, inside Docker, and on Linux/AWS, and must not lock the rest of the system to one OCR vendor.

## Options Considered

| Option | Local/offline | Windows dev | Docker/Linux | Printed text | Handwriting | Dependency size | Ease of testing |
|---|---|---|---|---|---|---|---|
| **Tesseract** (via `pytesseract`) | Yes — no network call | Needs a separate binary install (installer/choco); not pip-installable | One `apt-get install tesseract-ocr` line, ~30-50MB | Good (mature, widely used) | Weak — LSTM models trained mostly on printed text | Small: `pytesseract` is a thin wrapper (~50KB); the binary is a system package, not a Python wheel | Easy — deterministic per-run, but the *binary* isn't installed by `pip install`, so tests must not depend on it being present (see below) |
| **EasyOCR** / **PaddleOCR** | Yes, but pulls model weights from the internet on first use | Pure `pip install`, no separate binary | Works, but the image gets meaningfully larger | Good | Somewhat better on neat handwriting, still not reliable on cursive | Heavy — PyTorch/PaddlePaddle, several hundred MB to 1GB+ | Harder — first run needs network access to fetch weights unless pre-baked into the image; slower per-call |
| **docTR** / **TrOCR** (transformer-based) | Model weights typically fetched from a hub | Pure `pip install` | Works, heavy image | Good | Better than Tesseract for handwriting *if* a handwriting-tuned checkpoint is used | Heavy — transformers + torch | Similar network/weight-download friction as above |
| **Cloud OCR** (Google Vision / AWS Textract / Azure) | No — requires an external API and network | Trivial (just an HTTP client) | Trivial | Very good | Best available for handwriting | Tiny (just an SDK/HTTP client) | Requires mocking the API for tests, and real calls would send document content off-machine |

## Decision

**Tesseract**, via the `pytesseract` wrapper, as the one concrete `OCREngine` implementation (`backend/app/document_processing/ocr_tesseract.py`), installed as a system package (`apt-get install tesseract-ocr tesseract-ocr-eng`) in `backend/Dockerfile`.

## Rationale

- **No external service, ever**: satisfies "do not send document data to an external OCR service" outright — Tesseract runs entirely on the machine processing the document, no network call, nothing to mock for privacy reasons (only for determinism).
- **Docker/Linux/AWS story is trivial**: a single `apt-get install` line, ~30-50MB added to the image, no GPU, no model-weight download step, no runtime network dependency. This directly matters for later AWS deployment (any container runtime with a Debian/Ubuntu base gets the same one-line install).
- **Dependency size**: `pytesseract` itself is a ~50KB pure-Python wrapper; `pillow` (already needed for image validation regardless of OCR engine choice) is a normal, small wheel. Compare to EasyOCR/PaddleOCR/docTR/TrOCR, all of which pull in PyTorch or PaddlePaddle (hundreds of MB to >1GB) — a poor fit for "keep dependencies minimal."
- **Ease of testing**: the *logic* around OCR (confidence bucketing, line reconstruction, warning decisions — `_bucket_confidence`, `_reconstruct_lines`, `_build_warnings` in `ocr_tesseract.py`) is pure and unit-tested directly with synthetic data, no binary needed. The *processors* (`ImageProcessor`, `PDFProcessor`) are tested against a `FakeOCREngine` test double (`tests/document_processing/fakes.py`), never the real engine — see `docs/testing/README.md`. The real engine is validated only manually, inside Docker where it's actually installed (see the OCR section of `system-architecture.md` §8).
- **Windows local dev trade-off, accepted**: Tesseract is not `pip install`-able on Windows — a developer who wants to exercise the *real* engine locally (outside Docker) must install the binary separately (e.g. the UB-Mannheim Windows installer, or `choco install tesseract`) and ensure it's on `PATH`. This is a real, documented friction point, but it does not block development or testing: `pytest` never requires the binary (fake engine only), and `docker compose up` gets a working real engine automatically via the Dockerfile. Running the full stack (`docker compose up --build`) is therefore the recommended way to exercise real OCR, matching how this was actually verified (see the OCR section of `system-architecture.md`).

## Alternatives Considered (detail)

- **EasyOCR/PaddleOCR/docTR/TrOCR** — rejected for now primarily on dependency weight (PyTorch/PaddlePaddle) and the first-run model-download requirement, which conflicts with "keep dependencies minimal" and complicates fully-offline, deterministic CI. Any of these remain valid future `OCREngine` implementations if handwriting accuracy becomes a hard requirement — that is exactly what the `OCREngine` interface exists to make possible without touching `ImageProcessor`/`PDFProcessor`.
- **Cloud OCR APIs** — explicitly ruled out: the assignment requires no external service dependency for this phase, and clinical document content must not leave the machine.
- **Rendering full PDF pages to images** (e.g. via `pdf2image`/poppler or `PyMuPDF`) for the scanned-PDF path — not needed *for the common case*. `pypdf`'s existing `page.images` (already a dependency from the previous phase) reliably extracts a scanned page's embedded full-page image directly, verified experimentally against a synthetic reportlab-generated "scanned" PDF, and page-level `/Rotate` is corrected before OCR (see "Limitations" below). This avoids adding poppler (a system binary, more Windows/Docker friction) or PyMuPDF (a second PDF library) purely to solve a problem the existing dependency already solves for the dominant case — a genuine full page-rendering approach would still be a valid future upgrade for the gaps this doesn't cover (vector-rendered text, pixel-level skew), and would require changing only `PDFProcessor`'s internals, not the `OCREngine` interface it depends on.

## Confidence and Uncertainty

Tesseract's `image_to_data` call returns a real per-word confidence score (0-100), not a value this codebase invents. `_bucket_confidence` (in `ocr_tesseract.py`) deterministically buckets the *average* of those real per-word scores into the existing qualitative `ExtractionConfidence` model (`HIGH` ≥ 80, `MEDIUM` ≥ 50, else `LOW`; `None` when no text was detected at all — nothing to grade). This satisfies "preserve the engine's real confidence signal" without adding a second, numeric confidence field to `NormalizedDocument` alongside the existing qualitative one.

`OCR_LOW_CONFIDENCE` is attached by the engine itself when the bucket resolves to `LOW`; `IMAGE_QUALITY_LOW` is a separate, pre-OCR heuristic based on pixel dimensions (`image_quality.py`), asking a different question ("does the input look too small to OCR well?") before OCR even runs, rather than "how sure was the engine about what it read?" after.

## Handwriting

Tesseract's bundled models are trained on printed text; handwriting recognition is known to be unreliable and is **not claimed as a supported capability**. `TesseractOCREngine` attaches `HANDWRITING_MAY_REQUIRE_SPECIALIZED_MODEL` to every non-empty result — not because the input is detected as handwritten (no such detection exists), but as an honest, permanent disclaimer of this specific engine's limitation. This warning is deliberately attached by the *engine* (`ocr_tesseract.py`), not hardcoded into `ImageProcessor`/`PDFProcessor`: a future handwriting-capable `OCREngine` implementation simply would not emit it, with zero changes needed to either processor.

## Limitations (Scanned PDF) — do not read as "universal scanned-PDF support"

The scanned-PDF path (`PDFProcessor`'s OCR fallback, via `pypdf`'s `page.images`) is verified to handle the dominant real-world case, not every possible PDF construction:

- **Handled and verified**: a page whose scan is one or more embedded raster image XObjects (including one level of Form XObject nesting) — the output of essentially every scanner and mobile scanning app. A page-level `/Rotate` value (0/90/180/270) is corrected before OCR: `page.images` returns the image's raw stored bytes, unrotated, regardless of `/Rotate` — confirmed empirically by constructing a page whose *raw pixels* were genuinely sideways (simulating a scan captured on its side, with `/Rotate` compensating for display) and running it through the real Tesseract engine: uncorrected, OCR produced garbled, low-confidence text; rotating the extracted image by exactly `page.rotation` degrees before OCR (via `Image.rotate(page.rotation, expand=True)`) produced a clean, high-confidence result. Notably, the *sign* of the correction is not the intuitive one — a first attempt at `-page.rotation` reproduced the same garbled output as no correction at all, only the unnegated value fixed it. This was verified by testing, not assumed.
- **Not handled**: text rendered as vector graphics rather than a raster image (no image exists to extract — this is not an error, it just yields no OCR text, same as a genuinely blank page); a scan that is skewed/crooked at the pixel level with no corresponding page-level `/Rotate` (there is no metadata to correct against, and no skew-detection is implemented); a page with multiple embedded images gets all of them OCR'd and concatenated, with no logic to distinguish "the scan" from an incidental small image (e.g. a letterhead logo).
- This is a deliberate scope boundary, not an oversight: fixing the remaining gaps would mean rendering the full page (not just extracting an embedded image), which is exactly the "future replacement path" described above — swappable without touching `OCREngine` or `ImageProcessor`.

## Trade-offs

- No automated test exercises real Tesseract recognition end-to-end (by design — see "Ease of testing" above); confidence in the real integration, including the rotation-correction direction above, comes from manual verification inside the Docker container, documented in `system-architecture.md`.
- Windows-native local development without Docker requires a manual Tesseract install; this is a one-time developer-machine setup cost, not a blocker for `pytest` or for `docker compose up`.
- The confidence thresholds (80/50) are a coarse, documented heuristic, not a tuned/validated accuracy measurement — no such measurement has been performed, and none should be assumed from these numbers.
